# Review: mm service and mtm-scenario crate

Scope: `services/mm`, `crates/mtm-scenario`.

Reviewed 2026-10-14 at `bc96670`, read-only. Severity is
Critical/High/Medium/Low. Priority runs from P0 (now), P1 (next) and P2
(later) to P3 (nice to have). mm #1 and #2 were re-verified against the code
while compiling this report.

## services/mm

**Purpose and boundary.** Market makers. There is one `LocalSet` task per
configured maker, each with a derived wallet and one of three strategies:

- `clob-ladder` on Manifest;
- `clmm-range` on Orca or Raydium;
- `pool-arb` on any venue.

The service-boundary rule holds. Inside, though, strategy logic, LP execution,
state persistence and metrics are all mixed in the same `tick` functions.

**Design recommendations**

- **Plan, execute, persist (M).** A pure `plan(observation, params, state) ->
Vec<Action>`, an executor that runs actions through a venue LP trait, and an
  explicit phase machine (`Idle`, `Open`, `Closing{step}`,
  `Opening{pending_mint}`). Recovery becomes a function of the state file and
  the on-chain NFTs. This fixes #1-#4 structurally.
- **A shared `LpVenue` trait (M)** (open / close / position_value /
  discover_positions) in mtm-venues. Orca/Raydium dispatch is repeated today in
  mm, `scenario/teardown.rs` and `scenario/pnl.rs`.
- **One inventory valuation function (S)** (wallet + seat + positions), shared
  by mm metrics and pnl. The seat-locked accounting is duplicated in
  `clob.rs:82-96` and `pnl.rs:224-246`.
- **One execution profile per participant class (S):** CU margin, priority
  fee, slippage and rebroadcast policy.

## crates/mtm-scenario

**Purpose and boundary.** The shared library for scenario, mm, flow and arb:

- config for every service;
- env and address resolution, and deterministic wallets;
- the oracle `PriceBook`;
- venue price math (spot / marginal / size_to_target);
- swap execution and SOL/token funding.

It is becoming a grab-bag: pure math, transaction submission, minting, and
every service's config types all live here. It also pulls in all three venue
clients plus `mtm-dex-harness[cli]`.

**Design recommendations**

- **Split the crate (M):**
  - `mtm-scenario` keeps config, resolution and wallets;
  - pool math and execution move to `mtm-venues`;
  - funding becomes its own module or crate;
  - valuation becomes a shared `holdings` module.

  The rule: anything taking a `PoolSnapshot` belongs to venues, and anything
  that signs belongs next to `mtm-chain`.

- **Per-service config types live in their services (S).** Only the shared
  parts (tokens, programs, pools, participant identity) stay here.
- **One shared price feed per process (S):** a background-refreshed
  `watch::Receiver<PriceBook>` handed to every participant.

## Cross-cutting notes

- **No rebroadcast.** `mtm_chain::submit` sends once (`max_retries: 0`) and
  then only polls. Under load, dropped transactions surface only after 45 s or
  blockhash expiry, which turns congestion into stuck or orphaned LPs (with
  mm #1 and #3). Rebroadcast until expiry; size the CU limit from the
  simulation.
- **`!Send` signers are the root cause** of the LocalSet and OS-thread
  workarounds.
- **Hard-coded execution parameters** should become one configurable execution
  profile. Without priority fees, makers always lose to flow at high swap
  rates.
- **State and valuation exist in three places** (the mm state file, mm metrics,
  pnl's NFT discovery). Make on-chain discovery the source of truth.
