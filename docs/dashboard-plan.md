# Dashboard plan: observability + command and control

Status: P0 built (2026-10-16), on `feat/dashboard` (branched from `feat/hedge`);
P1–P3 proposed.

Decided (2026-10-16): custom UI **plus** Grafana; a dedicated testnet RPC
provider injected from Doppler (testnet runs 200 ms slots, 5 slots/s);
local single-operator first, multi-user later; feature gates from on-chain
state only, including every previously activated gate with its slot; keep
per-slot data for every run; Helius with the key in the URL, one key shared
by the scenario and the observer.

## Goal

One screen for a testnet run that answers three questions:

1. **What is the cluster doing right now?** Slots advancing, TPS, skip
   rate, block fullness, fees, versions, feature gates.
2. **What is our traffic doing on it?** Submitted / landed / failed per
   service, why they failed, how long landing took, what it cost, and the
   market health that already exists (makers, flow, arb, router, oracle).
3. **Did something change, and why?** Every feature activation, version
   rollout, epoch boundary and every change _we_ made sits on one timeline,
   so a shift in landing rate or CU cost can be lined up with its cause.

And one control surface to start, stop, reshape and ramp scenarios without
restarting the stack.

## What exists today

- Prometheus metrics from oracle, router, mm, flow, arb (`oracle_*`,
  `router_*`, `mm_*`, `flow_*`, `arb_*`), scraped on 9180-9184 by
  `ops/compose.scenario.yaml` (Prometheus 9190, Grafana 3100).
- `ops/grafana/dashboards/scenario.json`, generated by
  `bootstrap/scenario/dashboard.py`: market-health only (swaps, maker
  inventory, deviation vs oracle, arb PnL, router latency).
- `bootstrap/scenario/sample.py`: offline sampler of host CPU/RSS, TPS
  (`getTransactionCount` delta), slot rate, RPC latency — written to JSON,
  not to Prometheus.
- Lifecycle is `scenario.sh {deploy,up,bootstrap,status,snapshot,report,
measure,teardown,down}`; config is TOML profiles + scale overlays, read
  **once at startup** (no hot reload anywhere).

Gaps: nothing watches the cluster (slots, leaders, features, versions,
fees); transaction outcomes are only counted per service with service
labels, not uniformly at the submission layer; no event/annotation store;
no way to change a running scenario.

Custom UI plus Grafana (decided): Grafana is good at the
time-series half and stays, but it can't render a per-slot strip at
5 slots/s, has no forms for knobs, and annotations are its only notion
of events. The custom UI owns the live cockpit and C2; it links each panel
out to the matching Grafana panel for history. Both read the same event
store (control exposes it as a Grafana annotation source too), so a feature
gate shows up as the same vertical line in both.

Ports follow the scenario's range: chain-watch metrics 9185, control
8182 (API + UI). Everything binds loopback: the first version is one
operator on one machine, with no auth. Multi-user (auth, roles, remote
hosting) is a later phase; the API is shaped for it (every mutating call
carries an actor, recorded in the audit log) so it isn't a rewrite.

Every chart shares the timeline's x-axis; hovering a ◆ shows the feature's
id, description, activation slot, and a "compare before/after" button.

### Slot strip and timeline

Source: `slotSubscribe` (processed) for the tick, plus `getBlock` per slot
at `confirmed` (`transactionDetails: "full"`, `rewards: false`,
`maxSupportedTransactionVersion: 0`) from a worker pool that trails the tip
by a few slots. At 200 ms slots that is 5 `getBlock`/s sustained, plus
retries for slots that aren't available yet. Leaders from `getSlotLeaders` per epoch chunk; leader
identity → client/version from `getClusterNodes`.

Per slot we keep: leader, leader client + version, produced/skipped, block
time, tx count (vote / non-vote / ours), total CU, our txs' outcomes, fee
percentiles. Ring buffer of 18k slots (1 h at 5 slots/s) in memory for the
UI; every slot is written to the run store (see Retention) and kept. Prometheus gets aggregates only — per-slot cardinality doesn't
belong there.

Cell colours: produced, skipped, produced-with-our-failures, not yet
confirmed, and rooted later. Clicking a cell opens the block: our
transactions in it with signatures, CU, error, and an explorer link.

**Cost check:** full `getBlock` on every slot is 5 calls/s of large
responses, so chain-watch needs the dedicated provider (see RPC and
Doppler); it refuses `api.testnet.solana.com` for full-block mode. If the
provider offers Yellowstone gRPC, blocks and slots stream from it instead
of polling (same per-slot record, lower latency). Degraded mode: `transactionDetails: "signatures"` for
counts, and full blocks only for slots containing our signatures (known
from submission), which also keeps the "ours" columns exact.

### Feature gates

On-chain state only (decided) — no upstream schedule.

- Poll `getProgramAccounts` on `Feature111111111111111111111111111111111111`
  at start, at every epoch boundary and every 10 min. An account with
  `activated_at: Some(slot)` is active; one with `None` is **pending** and
  activates at the next epoch boundary.
- Names and descriptions from the `agave-feature-set` crate pinned to the
  same 4.x major as the other Solana deps (unknown ids are still shown, by
  pubkey).
- **Full history, not just the run window:** every feature account that
  exists is loaded, including gates activated long before the run, each
  with its `activated_at` slot. Slot → wall time via `getBlockTime`; for
  slots the provider no longer serves, estimate from the nearest known
  block time and the epoch schedule, and mark the time as estimated.
  The timeline can zoom out to "all gates on this cluster" and back in to
  the run.
- Timeline shows: activated (◆ at the activation slot), pending (hollow ◇
  at the next epoch boundary, with countdown). A pending gate observed
  becoming active during a run is flagged as "seen live" — the ones that
  get the automatic before/after compare.
- Stored in the run store as a `features` table (id, name, description,
  activated_at_slot, activated_at_time, time_estimated, first_seen_pending)
  so runs can be compared by which gates were active.
- Metric: `chain_feature_active{feature}` (0/1) and
  `chain_features_pending` — so Grafana and alerts can key off them too.

Feature-adjacent: **version rollouts**. Stake-weighted version
distribution from `getClusterNodes` + `getVoteAccounts`; an event when the
stake-majority version changes. On testnet behaviour shifts as often from a
rollout as from a gate.

### Catching behaviour changes

1. **Event lines everywhere.** Features, versions, epochs, our knob
   changes and run phases are events in one store; every chart draws them.
2. **Before/after compare.** Pick any event → side-by-side window (default
   ±1 epoch, or ±N min) of: landing rate, failure-kind mix, CU per
   action/venue, landing latency, skip rate by client, fees. Show deltas
   with a simple significance check (Mann-Whitney on per-slot samples) so
   noise isn't flagged.
3. **Automatic watch.** After each activation or majority-version change,
   control schedules a compare at +1 epoch and raises an alert if a metric
   moved past a threshold (e.g. CU per Orca swap ±3 %, a new error kind
   appears, landing rate −5 pts).
4. **Controlled experiments.** Pending gate → the C2 side can schedule a
   fixed, steady workload across the boundary (see playbooks) so the
   before/after is clean rather than mixed with our own ramps.
5. **Our own changes are suspects too.** Every knob change is an event, and
   `scenario_config_generation{service}` is a gauge, so "the landing rate
   dropped because I doubled the arb priority fee" is visible.

## Command and control

### Run lifecycle (wrap first, then go native)

Phase 1 control shells out to `scenario.sh` for `deploy / up / bootstrap /
status / snapshot / report / measure / teardown / down / janitor`, streams
its output to the UI, and records each step as an event. A run is
`{ target: local|devnet|testnet, profile, overlays: [x10, assets, …],
seed, notes }` persisted in SQLite with its timeline, so a past run can be
reopened and compared with another.

Later the supervisor moves into control (the review already asks for one
stop-with-escalation supervisor; scenario.sh's `stop()` is the template),
and scenario.sh becomes a thin CLI over the control API.

### Compose (built)

The Control tab opens with a Compose panel: start from a preset or an
existing overlay, then choose the tokens (the 11-token catalog), the
venues per `<token>/USDC` pair, Orca cross pools, makers per pool by kind,
maker capital (or sized to the flow), takers with their trade rate and
sizes, and arb bots. Each change re-runs the estimate
(`POST /api/compose/estimate`, crates/scenario-spec): expected tx/s by
actor, compute per block, headroom against this host's execution rate, the
block limit and the busiest pool's account limit, the venue split, the
bootstrap size and SOL needs. A target tx/s sizes the takers. "Write
overlay" (`POST /api/compose`) renders and checks
`config/scale-<preset or c-hash>.toml`; "Write and run up" also starts `up`
with it. An existing overlay is never rewritten.

Not yet: targeting a share of transactions per venue. Today the split is
emergent (the router takes the best price) and the estimate uses shares
calibrated from the x1500 runs. Targeting would make those shares a spec
input and need the flow to steer routes, e.g. a per-trade venue
restriction passed to the router.

### Live knobs

Today config is read once. Each long-running service gets a loopback admin
listener and a `tokio::sync::watch<Knobs>`; loops read the current value at
the top of each tick, so a change applies within one tick and nothing
restarts.

| Service | Hot knobs                                                                                                                                                                                           | Needs restart              |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| flow    | `rate_per_min`, `median_usd`, `sigma`, `large_probability`, `large_multiplier`, `exact_out_probability`, `slippage_bps`, enabled `pairs`, `takers` (spawn/stop tasks), pause                        | inventory, rng seed        |
| mm      | per maker: pause, `interval_ms`, strategy params (`spread_bps`, `levels`, `step_bps`, `level_size`, `width_bps`, `recenter_bps`, `skew_bps`), priority fee, CU limit; hedge on/off, hedge cost/band | venue, pair, strategy kind |
| arb     | per bot: enabled, `min_profit_usd`, `max_legs`, priority fee, latency; `poll_ms`, `debounce_ms`                                                                                                     | start tokens               |
| global  | pause all / resume, global priority-fee multiplier, CU-limit policy (exact-from-sim vs fixed)                                                                                                       | pools, tokens, programs    |

API: `GET /admin/knobs`, `PATCH /admin/knobs` (JSON merge patch validated
against bounds, returns the new generation). Control fans out, records the
diff as an event, and can persist overrides to the run so a restart keeps
them. The UI shows a diff preview before applying. Changing a "needs
restart" field offers a rolling restart of that service.

### Playbooks

Declarative, time- or event-triggered sequences of knob changes, stored as
TOML next to the profiles:

- **Ramp**: flow from X to Y tx/s over N min in steps; stop on landing rate
  < threshold (finds the knee).
- **Burst / spike**: 10× flow for 60 s, then back.
- **Soak**: fixed load for hours (the long-run findings: drift, ledger
  growth).
- **Contention**: route all flow through one pool → write-lock contention
  and `AccountInUse`-style failures.
- **CU-heavy**: multi-hop routes / large exact-out; shows CU-limit edges.
- **Fee war**: arb bots escalate priority fees against each other.
- **Gate straddle**: on "feature X pending", hold steady load from −30 min
  to +1 epoch past the boundary, then auto-compare.

Triggers: at time, at slot/epoch, on event (feature pending/activated,
alert), on metric threshold. Running playbooks show as bars on the
timeline.

### Safety (testnet is shared)

- **Kill switch**: header "PAUSE ALL" sets every service's pause knob; a
  second level stops processes.
- **Budget guard**: SOL spend per hour and per run caps; control pauses
  flow/arb when burn exceeds the cap or the faucet runway drops below N h.
- **Rate guard**: hard ceiling on our TPS per target, separate from the
  knob (so a typo can't flood testnet).
- **Confirm destructive actions**: deploy (an upgrade of a live program —
  the open review item), teardown, janitor; show the exact command.
- **Audit log**: who/what/when/diff for every action, as events.
- **Access**: loopback only, no auth, for the first version (decided).
  Later: a bearer token from Doppler, then operator vs read-only roles.

## RPC and Doppler

Provider: **Helius**, authenticated by the API key in the URL. One key
serves both the scenario and chain-watch (decided), so nothing new is
required: chain-watch uses `SCENARIO_RPC_URL` / `SCENARIO_WS_URL` (already
in Doppler's optional list) and the optional `CHAIN_WATCH_*` pair overrides
them if a second key is ever wanted. URLs are never logged, stored or
labelled — only the host (`rpc::host`, `rpc::redact`).

| Doppler variable                            | Required | Maps to                                   | Notes                                                          |
| ------------------------------------------- | -------- | ----------------------------------------- | -------------------------------------------------------------- |
| `SCENARIO_RPC_URL`                          | testnet  | `MTM_RPC__HTTP_URL` (every service)       | `https://<host>/?api-key=…`                                    |
| `SCENARIO_WS_URL`                           | no       | `MTM_RPC__WS_URL`                         | defaults to the HTTP URL with `https`→`wss`                    |
| `CHAIN_WATCH_RPC_URL`, `CHAIN_WATCH_WS_URL` | no       | `MTM_CHAIN_WATCH__RPC__{HTTP_URL,WS_URL}` | only to give the observer its own key; WS derived the same way |

As built: `scenario.sh` exports these per target (the config loader splits
`MTM_` env on `__`); `just scenario-watch-{dev,testnet}` and `up` run under
`doppler run`. Against a public endpoint chain-watch records slots and
leaders only (`block_details = "slots"`: produced / skipped and the leader's
client from `getBlocks`, TPS from performance samples) under a 6 requests/s
budget, unless `allow_public_block_fetch` is set. Every 429's `Retry-After`
pauses all callers. (Measured 2026-10-16: fetching a block per slot from
api.testnet.solana.com exhausted its endpoint quota within minutes.)

**To check before the first testnet run:** that the Helius plan serves
_testnet_ (Helius documents mainnet and devnet; testnet support was not
confirmed), and what full `getBlock` at 5/s costs in credits on that plan.
Yellowstone gRPC (Helius "LaserStream") is plan-dependent and its testnet
availability is unconfirmed too; chain-watch polls today, and a gRPC source
would replace `slots::subscribe` + the `getBlock` loop behind the same
per-slot record (`CHAIN_WATCH_GRPC_URL` / `_TOKEN` when it exists).

## Retention

Keep every slot of every run (decided), so a run can be reopened and
drilled into long after it ended.

- **Run store:** one SQLite file per run, `.scenario/runs/<run-id>/run.db`
  (WAL; chain-watch and control write, the UI reads). Tables: `slots`
  (one row per slot, observed or skipped), `txs` (every transaction we
  submitted: signature, service, actor, action, venue, slot sent / landed,
  outcome, error, CU used / requested, fee, priority fee), `events`
  (features, versions, epochs, knob changes, alerts, run phases),
  `features`, `knobs` (every generation of every service's knobs).
- **Size:** slots are small (~5 MB/h at 5 slots/s). Our transactions
  dominate: ~70 MB/h at 100 tx/s. A multi-hour soak at scale is a few GB —
  fine on local disk; `control runs prune` deletes runs explicitly, never
  automatically.
- **Raw blocks (optional, for the deepest dives):** zstd-compressed raw
  `getBlock` JSON in `blocks/` beside `run.db`: off / blocks with one of our
  failed transactions (default) / blocks with any of ours / all. "Ours" was
  the first default, but at scale every block holds one of ours: a 2 h x1000
  run stored about 6 GB of raw blocks (4 GB/h) beside a 3.4 GB `run.db`.
- **Analysis:** `control runs export <id>` writes Parquet so DuckDB or a
  notebook can query one run or many; the UI's run-vs-run compare reads
  `run.db` directly.
- **Prometheus:** set retention explicitly (`--storage.tsdb.retention.time=90d`;
  the review noted none is set) — it holds aggregates for Grafana, the run
  store holds the detail.
